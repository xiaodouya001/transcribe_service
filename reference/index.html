2. 接入模式选型

根据 Fanolab 接口要求，系统支持两种长连接模式。点击下方按钮，查看 WebSocket 与 SSE (Server-Sent Events) 在当前架构下的不同优势与适用场景。

🔄

全双工即时通信

适用于需要心跳维持或配置指令下发的双向通信场景。客户端与服务端保持持久连接。

  • ✓ 极低报头开销： 握手后数据帧极小，适合高频短文本传输。
  • ✓ 双向通信： 允许系统向 ASR 引擎实时发送动态配置或控制指令。
  • ! 架构挑战： 需要自行实现复杂的断线重连与心跳保活（Ping/Pong）机制。
⬇️

轻量级单向数据流

若仅需单向接收 JSON 流，基于标准 HTTP 协议的 SSE 是更轻量、对云原生网关更友好的选择。

  • ✓ 天然重连机制： 浏览器/客户端内置 Last-Event-ID 支持，断线自动恢复。
  • ✓ 极佳兼容性： 完全基于 HTTP/1.1，与 AWS ALB (Application Load Balancer) 等网关组件完美兼容。
  • ✗ 单向限制： 只能由服务端向客户端推数据，无法用于发送控制指令。

3. 核心处理链路：防抖去重演示

在真实网络环境下，ASR 引擎由于网络抖动，经常会将同一时间戳的片段重复推送。本节模拟了利用 Redis SETNX 指令实现的亚毫秒级精准去重机制。只有抢到“锁”的数据才会被放行至 Kafka。

模拟控制面板

点击下方按钮，模拟网络抖动导致 ASR 引擎瞬间发送两条完全相同的转录 JSON。

Redis 逻辑:
SETNX dedup:{session}:{timestamp} 1
如果返回 1 (成功): 数据放行 Kafka。
如果返回 0 (失败): 判定为重复，直接丢弃。

4. 生产端分发：吞吐量与延迟的权衡

为了保证高吞吐下的低延迟，aiokafka 异步 Producer 需进行严格调优。调节 linger_ms 参数（等待更多消息打包发送的时间）是关键。观察下方图表，了解增加 linger_ms 如何在提升整体吞吐量的同时，略微增加单条消息的延迟。

0ms (极致低迟) 100ms (高吞吐批量)
报告建议设定为 10-20ms，在单条消息即时性与批量吞吐量间取得最佳平衡。并开启 lz4 压缩。
